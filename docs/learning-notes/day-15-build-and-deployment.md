## 一、今天要交付什么

今天不是继续加功能，而是让“自己电脑上能运行”的网站变成“别人可以通过网址访问”的网站。

完成标准：

2. 完成本地生产构建和权限验收。
3. 将检查过的代码版本部署到 Vercel（网站托管平台）。

5. 验证线上公开页面、登录、后台及私有项目权限。
6. 留下一份不含密码和密钥的部署记录。

默认选择 Vercel，是因为它直接支持 Next.js 的服务端功能，初次部署配置较少，不代表只能使用它。也可以选择支持 Node.js（JavaScript 服务端运行环境）的主机，但需要自己管理进程、HTTPS（加密网络连接）等更多内容。[官方 Next.js 集成说明](https://vercel.com/docs/frameworks/full-stack/nextjs)

## 三、三个命令，三种工作

| 阶段 | 命令 | 通俗解释 | 适合谁使用 |
| --- | --- | --- | --- |
| 开发 | `npm run dev` | 边改代码边查看，提供开发错误提示 | 写代码的你 |
| 构建 | `npm run build` | 编译、检查并生成生产运行产物 | 发布前执行 |
| 生产运行 | `npm run start` | 运行已经构建好的版本 | 本地模拟正式运行或自管服务器 |

`npm` 是包管理工具，`run` 表示执行 `package.json` 的脚本。`build` 和 `start` 是本项目定义的脚本名称。

为什么开发正常还要构建？开发时可能只访问了少量页面，正式构建会执行更多编译与页面生成工作；生产模式下也没有相同的热更新行为。开发模式通过不是生产模式通过。

构建产物保存在 `.next`，不是源代码备份。它会被构建命令更新，不需要提交到 Git（版本管理工具）。Vercel 从源代码自行构建，不需要你上传本地 `.next`。

## 四、任务 1：上线前先守住权限边界

先在本地网站连接现有数据库验收。只创建没有真实敏感信息的测试记录。

| 身份与操作 | 标准结果 |
| --- | --- |
| 未登录访问公开项目 | 可以看到 |
| 未登录访问私有项目的已知地址 | 显示不存在，正文和标题不泄露内容 |
| 管理员打开公开网站 | 也只看到公开项目 |
| 管理员打开后台 | 可以看到私有和公开项目 |
| 未登录打开后台地址 | 要求登录 |
| 普通登录用户打开后台或尝试写入 | 被拒绝，数据未改变 |
| 新建项目 | 默认私有 |
| 管理员公开项目 | 公开列表与详情可以访问 |
| 管理员重新设为私有 | 刷新公开页后不再显示，详情不可访问 |
| 匿名身份直接查询私有项目及其亮点、标签关联 | 查不到私有记录 |

页面隐藏按钮只是显示控制。RLS（行级安全）才负责限制数据库允许读取、修改哪些行；服务端写操作也需要验证管理员身份。这些检查各有职责。

数据库控制台里的 `postgres` 是高权限身份，看到数据不代表匿名访客也能看到。测试时必须确认使用的是目标身份，沿用 Day 14 的权限验收方式。

如缺少普通用户测试条件，明确记录“未测试”，不要写“通过”。公开前完成这项验证；不要通过关闭 RLS 来绕过错误。

远程迁移状态可用以下只读命令检查：

```powershell
npx supabase migration list --linked
```

`npx` 运行项目中的命令工具；`migration list` 列出迁移记录；`--linked` 指向已关联的远程项目。预期本地与远程都包含 Day 14 的 `20260903063825` 迁移。如果不一致，先核对关联项目和 SQL（数据库操作语言），不要盲目推送。

今天不要再运行 `--include-seed`。Seed（种子数据）用于初始化，不是日常部署步骤，重复执行的影响取决于文件中的实际 SQL。

## 五、任务 2：在本地跑一次生产模式

在项目根目录执行：

```powershell
node --version
npm --version
npm run lint
npx tsc --noEmit
```

前两个命令只打印运行环境和包管理工具的版本。`lint` 检查代码规范；`tsc` 是 TypeScript 编译器，`--noEmit` 表示不输出编译后的 JavaScript 文件，配置可能仍让它更新增量检查缓存。预期检查正常结束，没有错误。

接着构建。这个命令会更新本地 `.next` 产物，不会替你部署数据库或网站：

```powershell
npm run build
```

预期看到编译完成、页面生成完成、路由列表，最后正常返回终端提示符。只看到 `Creating an optimized production build` 不能视为成功。

### 如果和本次一样默认构建停住

先保存终端输出，再用 `Ctrl+C` 结束自己刚启动的构建。然后使用已在本次检查通过的对照方式：

```powershell
npm run build -- --webpack
```

第一个 `--` 告诉 npm：后面的参数交给脚本；`--webpack` 让 Next.js 使用 Webpack（打包工具）构建。它不改变页面业务逻辑，也不修改 `package.json`。

如果使用这条命令通过，今天可以在托管平台将构建命令也设为 `npm run build -- --webpack`，保持一致。记录默认构建问题尚未定位，不能说已修复。不要在本地使用一种构建方式，却假定云端另一种也必然通过。

若两种都失败，先处理第一条真正的错误，再继续部署。不要删除项目外的锁文件来碰运气。此次构建出现过父目录锁文件提示，但提示本身不足以确定原因。

构建成功后运行生产版本，以下命令会启动一个持续运行的本地服务：

```powershell
npm run start -- --hostname 127.0.0.1 --port 3001
```

`--hostname 127.0.0.1` 限制在本机访问；`--port 3001` 选择 3001 端口，避免和常用开发端口冲突。打开 `http://127.0.0.1:3001`，重复上一节验收。结束时在这个终端按 `Ctrl+C`，不需要结束电脑上全部 Node.js 进程。

注意：`localhost` 与 `127.0.0.1` 是不同主机名，浏览器登录 Cookie（会话小数据）不会当然共用。换地址后需要重新登录不是会话丢失的充分证据。

## 六、任务 3：准备一个可追溯的代码版本

云端通常构建 Git 里的某次 Commit（提交快照），不是你电脑里未保存或未提交的文件。本次检查时，Day 14 的修改尚未全部提交。

先执行只读检查：

```powershell
git status --short
git diff --stat
git check-ignore .env.local
git ls-files .env.local
```

分别查看：改动列表、改动规模、环境文件是否被忽略、环境文件是否已被跟踪。预期第三条输出 `.env.local`，第四条没有输出。

如果第四条出现文件名，先停止发布：忽略规则不会把已经跟踪的文件自动移出历史。若密钥曾推送出去，需要处理泄露和撤销密钥，仅删除当前文件不够。

在编辑器中逐项审阅、暂存本次代码和必要文档，再使用编辑器完成提交。提交会记录文件快照，不会自动发布网站。不要不看文件就全选暂存，更不要提交 `.env.local`、数据库密码或访问令牌。

确认远程仓库和目标分支后，才自行推送。Push（推送）会把提交发送给远程服务；仓库若已经绑定部署平台，推送生产分支可能立刻触发正式发布。私有仓库也可以接入平台，无须为了部署改成公开仓库。

保留并提交项目现有的 `package-lock.json`（依赖锁文件），继续使用 npm，不混用其他包管理工具。云端全新安装可以使用 `npm ci`：按锁文件安装，若已有 `node_modules` 会先重新创建依赖目录。无需为了本课在当前工作目录无故重装依赖。

## 七、环境变量：名字一样，存放位置不同

本地 `.env.local` 不会自动上传。云端必须另外配置环境变量，供云端构建和运行使用。

| 名称 | 填什么 | 注意事项 |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | 当前 Supabase 项目地址 | 不是网站的 Vercel 地址 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 同一 Supabase 项目的可发布密钥 | 可用于公开客户端；安全依赖权限策略 |
| `ADMIN_USER_ID` | 当前指定管理员的用户 ID（标识） | 服务端配置，必须与数据库管理员策略一致 |

以上是本项目实际使用的变量名，不要从其他教程抄成另一个名称。平台表单中分别填名称和值，不把整个 `.env.local` 粘到一个值里，也不要额外加包裹引号。

`NEXT_PUBLIC_` 表示该变量允许进入浏览器代码，相关值可能在构建时固定。它不是秘密保险箱。平台把某值标成 Secret（秘密值），也不能阻止你通过客户端代码把它公开。

不要填入 `service_role` 高权限密钥、数据库密码或 Supabase CLI（命令行工具）的登录令牌。当前网站不需要靠这些秘密绕过权限。

Production（生产）、Preview（预览）、Development（开发）是不同配置范围。选择本次部署需要的范围。环境变量修改不会自动改变旧部署，需要重新部署。[环境变量官方说明](https://vercel.com/docs/environment-variables)

预览环境不是数据库隔离：如果预览和生产使用相同 Supabase 地址，两个网站操作的就是同一批数据。本课可以继续使用个人学习项目，但只能用明确标记的测试记录。以后真实使用时再考虑独立测试项目。

## 九、Supabase 登录配置：不要混淆两种网址

网站网址可能是 `https://你的项目.vercel.app`，Supabase 项目地址是 `https://项目标识.supabase.co`。前者让访客访问网页，后者让代码访问后端，不能互相替换。

本项目目前使用 `signInWithPassword`（邮箱密码登录），登录成功后代码跳转 `/admin`。没有实现第三方登录回调路由，所以不需要凭空创建或配置一个 `/auth/callback` 来“修复登录”。

在 Supabase 的身份认证网址设置中，可以把 Site URL（站点地址）设为稳定的正式网站地址。它主要影响没有单独指定跳转地址时的默认跳转，例如确认邮件、密码重置等流程；不是所有登录故障的通用修复项。

只有实际实现了需要回调的流程，才将该流程的准确地址加入 Redirect URLs（允许跳转地址）。不要允许所有人的 `vercel.app` 地址；精确生产地址比宽泛通配更安全。本课不要求额外实现邮件确认或重置密码。[Supabase 跳转地址说明](https://supabase.com/docs/guides/auth/redirect-urls)

## 十、任务 5：线上验收——构建绿色不代表全部完成

部署成功先记下：提交编号、构建命令、环境范围、正式网址。然后使用新开的无痕窗口验收，避免本地登录状态干扰。

按顺序完成：

1. 首页、项目列表、公开详情、工具页均能打开。
2. 私有项目不出现在首页和列表；已知私有地址不可访问，页面标题不泄露名称。
3. 未登录访问后台被要求登录。
4. 管理员登录成功，刷新仍然能访问后台；退出后不能继续管理。
5. 普通登录用户不能管理或修改数据。
6. 新建一个无敏感信息的测试项目，默认私有；公开后在无痕窗口可见；改回私有后刷新不可见。
7. 修改测试记录后，相关公开页面显示预期结果。记住首页工具当前仍为静态数据。
8. 仅删除自己刚创建的测试记录，确认列表与详情均更新。删除可能不可恢复，不要用已有真实项目测试。
9. 检查平台运行日志没有持续报错，也没有输出密码或完整令牌。
10. 回到 Day 14 检查匿名身份不能直接读取私有项目的关联表数据。

这里的网站地址可能对任何人开放。平台的 Deployment Protection（部署保护）与应用自己的管理员登录是两层不同的权限。Hobby 的标准保护不保护生产域名，不能因为某个预览链接要求平台登录，就推断正式网站也保密。[部署保护说明](https://vercel.com/docs/deployment-protection)

## 十一、出错时按阶段定位

| 现象 | 先检查什么 | 不该先做什么 |
| --- | --- | --- |
| 安装失败 | 锁文件、包管理工具、Node.js 版本、安装日志 | 随机切换包管理工具 |
| 构建卡住或失败 | 第一条实际错误、本地与平台构建命令 | 把尚未结束的任务记作通过 |
| 本地成功、云端找不到文件 | 文件是否提交、导入路径大小写是否准确 | 只在本地改名却不检查 Git |
| 页面访问时才报错 | 运行日志、变量名称及范围、Supabase 地址 | 认为构建成功就排除后端问题 |
| 登录失败 | 邮箱密码、账号状态、云端环境变量与具体错误 | 直接关闭权限或随便新增回调路径 |
| 登录成功但不是管理员 | `ADMIN_USER_ID` 与当前用户、RLS 管理员配置 | 给所有已登录用户写权限 |
| 项目全部消失 | 是否仍为私有、迁移是否匹配、查询是否报错 | 把空列表当作数据库丢失 |
| 更新环境变量后没变化 | 是否创建了新部署、当前访问哪个网址 | 反复只刷新旧部署 |
| 预览测试影响正式数据 | 是否连接同一 Supabase 项目 | 把预览环境当作自动隔离数据库 |

Build Logs（构建日志）说明“能否生成应用”；Runtime Logs（运行日志）说明“有人访问时出了什么问题”。贴错误时保留错误文字和相关文件名，遮住密码、令牌、Cookie，不要发整份环境文件。

## 十二、知道怎么退回，才能放心发布

Rollback（回滚）通常是将网站切回某个以前的部署版本，不等于撤销数据库迁移，也不等于恢复被删除的数据。

回滚前要确认旧代码仍兼容当前数据库和权限要求。特别注意：不能直接退回还使用静态项目数据的 Day 13 版本，它可能继续展示后来已设为私有的内容。优先选择已经具备 Day 14 私有过滤能力、且验证过的版本。

如果出现权限泄露，先采取能有效阻止继续访问的措施并核实结果，再定位问题；不要只修页面显示而保留数据库开放读取。已经公开的信息可能已被别人保存，改为私有无法追回副本。

## 十三、自测题与标准答案

先自己回答，再对照。能说出原因比背命令重要。

1. **为什么 `dev` 正常不代表可以上线？**  
   标准答案：开发环境和生产构建执行的工作不同，未访问的页面、编译和运行配置仍可能出错，还必须验证生产运行及权限。
2. **构建成功证明数据库权限正确吗？**  
   标准答案：不能。权限需要在不同真实身份下验证读取、写入及被拒绝的结果。
3. **为什么不能把这个网站当作 Vite 静态站点上传 `dist`？**  
   标准答案：当前 Next.js 项目依赖服务端登录、操作和动态查询，需要对应服务端运行能力。
4. **`.env.local` 被忽略，云端为什么还要配置？**  
   标准答案：它不在上传的代码里，云端环境独立，需要另行提供变量。
5. **可发布密钥公开后，数据库就没有安全性了吗？**  
   标准答案：不是。该密钥用于识别项目访问，真正的数据权限由授权及 RLS 等规则限制；规则配置错误才会造成越权。
6. **能不能把 `service_role` 放进 `NEXT_PUBLIC_` 变量？**  
   标准答案：不能。这个前缀允许值进入浏览器，高权限密钥不能暴露给访客。
7. **预览网站一定使用测试数据库吗？**  
   标准答案：不一定。连接地址相同就可能操作同一个数据库，需要自己隔离配置。
8. **在 Supabase 中改 Site URL 能解决所有密码登录问题吗？**  
   标准答案：不能。本项目密码登录后由代码跳转；应按错误检查账号、变量、会话与权限。
9. **为什么需要记录提交编号？**  
   标准答案：知道上线的是哪一份代码，才能复现问题、对照变更并判断回滚目标。
10. **`npm run build -- --webpack` 中两个参数有什么作用？**  
    标准答案：`--` 将后续参数转交脚本，`--webpack` 指定 Next.js 的构建工具。
11. **更新环境变量之后只刷新页面够吗？**  
    标准答案：不够。平台变量变更需要新的部署，客户端相关值还可能在构建时固定。
12. **第一次点击 Deploy 一定只有自己能看到吗？**  
    标准答案：不一定，可能直接产生公开生产站点，必须先过发布检查。
13. **回滚网站能恢复删除的项目吗？**  
    标准答案：不能，网站代码与数据库记录是不同状态；数据恢复需要适当的备份或恢复机制。
14. **为什么不能随便回滚到 Day 13？**  
    标准答案：旧版本可能读取静态项目数据，不遵守新的私有状态，造成重新公开。
15. **后台修改工具后首页没变，一定是缓存错误吗？**  
    标准答案：不一定，当前首页收藏工具仍读取本地静态数据，先确认数据来源。
16. **默认构建没完成，但 Webpack 构建通过，应该怎么写结论？**  
    标准答案：记录 Webpack 对照构建通过、默认构建问题未定位；部署采用已验证的构建命令，不能笼统说全部构建问题已修复。
