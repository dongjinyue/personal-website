# GitHub Actions 自动部署设计

## 目标

将 `main` 分支推送到 GitHub 后，自动更新腾讯云服务器上的个人网站；保留手动触发入口，并让构建或服务重启失败能在 GitHub Actions 日志中明确失败，而不是误报成功。

## 当前已知情况

- 服务器项目目录为 `/home/ubuntu/apps/personal-website`。
- 服务器运行着 Next.js `next start` 进程；目前检查没有发现个人网站对应的 systemd 服务或 Docker 容器。
- 项目使用 `package-lock.json`，本地部署依赖应使用 `npm ci`，之后运行生产构建。
- 服务器上的环境文件、Obsidian 知识库目录、反向代理和现有监听端口必须保留；不能将密钥写进 GitHub 日志或代码。
- 尚未确认当前进程的启动父进程、代码目录所有者、Node/npm 的绝对路径、网站监听端口、反向代理配置及 GitHub Actions 所需凭据。

## 方案选择

1. **GitHub Actions 通过 SSH 部署，并由 systemd 管理网站（推荐）**：每次推送后立即触发，发布状态和日志集中在 GitHub；需要配置部署 SSH 密钥，并在服务器首次安装服务单元。
2. **服务器定时拉取 GitHub**：无需从 GitHub 连接服务器，但更新有轮询延迟，失败日志分散在服务器。
3. **服务器接收 GitHub Webhook**：触发及时，但要额外开放并保护一个公网接口，维护成本和攻击面都更大。

选择方案 1。

## 部署流程

1. `.github/workflows/deploy.yml` 在 `main` 收到推送时触发，并提供 `workflow_dispatch` 手动重跑入口；限制并发，避免同一服务器同时发布两个版本。
2. Workflow 使用 GitHub 仓库机密项保存服务器地址、SSH 端口、部署用户名、私钥和经过核验的 SSH 主机公钥；不得使用 `StrictHostKeyChecking=no`，不得把私钥回显到日志。
3. Workflow 通过 SSH 在 `/home/ubuntu/apps/personal-website` 执行远程发布命令。命令先检查工作树无本地改动，再对 `main` 执行快进更新，最后调用仓库中的部署脚本；这样新脚本也会先随代码更新到服务器。
4. 部署脚本串行执行 `npm ci`、`npm run build`、重启 `personal-website.service`，再对本机网站地址做 HTTP 健康检查。发布完成后记录实际部署的 Git 提交号。
5. systemd 单元以非 root 的 `ubuntu` 用户运行生产服务；SSH 部署身份只获得重启该指定服务所需的最小权限。

## 失败处理与安全边界

- 任一工作树检查、更新、依赖安装、构建、重启或健康检查失败，部署流程以非零状态退出，使 GitHub Actions 标记失败并保留日志。
- 构建失败时不主动重启服务；构建在当前项目目录执行，需接受构建期间可能出现短暂服务波动。部署不执行数据库迁移，不触碰新闻采集器或 Obsidian 同步定时器。
- 自动发布仅响应 `main` 的推送；其他分支和 Pull Request 不直接部署。
- 首次安装 systemd 服务和部署账号/密钥属于一次性服务器初始化，不由公开工作流自动提权完成。
- 使用独立部署密钥和受限权限；不能在仓库提交生产环境变量、密码或私钥。

## 实施前服务器核验

开始修改线上服务前，先确认 Next.js 进程父进程及当前启动命令、`/home/ubuntu/apps/personal-website` 的所有者和 Git 状态、Node/npm 路径、监听端口与反向代理目标，以及部署用户是否能安全读写仓库。若线上目录有未提交改动，部署脚本必须停止并报告，不能覆盖。

## 验收标准

- 推送到 `main` 会启动单一部署任务；手动触发也可运行同一流程。
- Actions 日志不包含私钥或环境变量值，SSH 主机身份校验保持开启。
- 服务器成功快进到部署时最新的 `main` 提交，构建成功，指定 systemd 服务重启成功，本机健康检查返回成功状态，并能从日志确认实际部署提交号。
- 构建或健康检查失败时，Workflow 显示失败；不会报告发布成功。
- 服务器原有环境文件、知识库挂载/路径、反向代理和新闻/Obsidian 定时任务保持不变。

## 明确不包含

- 不迁移到 Vercel 或其他托管平台。
- 不修改新闻采集频率、Obsidian 同步方式或数据库结构。
- 本阶段不承诺跨版本原子切换或自动回滚；如需零停机/回滚，再作为单独改进设计。
